## 2026 年 8 月实现范围记录

以下是该历史分支截至 `daa7e52285cc26a5c09c81c3c8a28688fff17b63` 的实现说明，不能代替当前源码、部署配置或新版支付合同。

### Agent 使用计费

- 浏览器每次真实发送携带 UUID `usageId`；网络结果不确定时持久化并复用原值。
- Runtime 在同一数据库事务中锁定 Session 和 `usageId`，完成额度预留、Turn 与用户 Message 创建。
- Agent 创建者免计费；免费额度按使用者与 Capability 隔离，Capability 版本更新不重置额度。
- 免费额度与钱包只在 Turn 成功后结算；失败、中断、空闲超时、关停和清扫释放预留。
- 相同 `usageId` 与相同请求指纹返回原 Message，不再次启动 Agent 或扣费；不同指纹返回幂等冲突。
- 免费额度耗尽且钱包余额不足时，在创建 Turn 和调用 Agent 前返回 HTTP 402。
- 不可变 `wallet_ledger` 只追加充值 credit 或使用 debit；应用角色无 UPDATE/DELETE 权限。

当时源码提供配置化固定按次收费策略；本记录不证明 Production 已启用：

- `RUNTIME_BILLING_FREE_USES`
- `RUNTIME_BILLING_UNIT_PRICE_CENTS`

该历史分支没有实现“预留最大预算、按模型实际用量结算并释放差额”。当时 Runtime 没有经过业务合同定义和持久化的可信计费量，也没有总 token/总成本硬上限。数据库为 `settled_cents < reserved_cents` 留有结构空间，但在明确币种、定价版本、舍入、最低收费、超预算处理和崩溃补偿前，不得直接用 Pi 消息中的浮点 cost 扣用户余额。

### 钱包充值

- Authoring 提供钱包、手动金额创建充值订单、按订单查询和按充值 intent 恢复。
- 支付方式仅有二维码支付（C扫B）`/v3/prepay`；查单使用 `/v3/queryorder`。H5 收银台已在迁移 `0011` 移除，历史 `h5` 订单迁到 `qr`。
- 测试和正式网关由固定枚举选择；正式网关还需要独立开关、production 进程和 production 发布身份三重条件。
- 下单 POST 有超时但没有自动重试。结果不确定时保持原 `pay_trace_no`，只查原订单。
- 网关响应与回调都验签并核对环境、机构、商户、支付流水、时间、金额和平台订单号。
- 回调与主动查单共用同一个事务入账函数：订单成功、钱包增加和充值流水共同提交。
- 回调可重复；同一充值订单只能产生一条 credit 流水。
- 前端只展示后端允许的二维码内容，只轮询 Combo 内部订单状态。
- 支付入口失效或订单未知时，用户可以放弃原 Agent 任务；旧充值订单仍保留并继续查账，迟到成功仍会入账。

### 运行配置边界

- Runtime 清单显式注入免费次数和固定单价。
- 乐收赢配置逐项只注入 Authoring API；worker 与 Runtime 不接收机构密钥。
- 支付配置缺省时网关关闭。启用后缺少机构、商户、密钥或合法 HTTPS 回调地址会拒绝启动。
- 支付 Secret 只通过 `secretKeyRef` 引用，不进入仓库、ConfigMap、日志或测试输出。

## 后续 Test 人工检查步骤（计划）

以下是经 2026-08-31 修订的检查计划，不是执行记录。迁移 `0016` 仅指该次兼容切片，不能作为当前迁移 head；再次执行前须依据候选源码与 [`deployment-topology.md`](deployment-topology.md) 核对适用步骤，并在源码门禁通过、获得后续部署授权和完成专用测试配置后执行：

1. 先核对已部署 Test 的 `0012`–`0016` 不可变兼容前缀与候选源码字节完全一致，再把物理隔离的 Test 数据库连续迁移到候选 head（本兼容切片为 `0016_project_history_agent_flow.sql`），并用专用应用角色运行 PG 测试。
2. 仅给 Authoring API 注入乐收赢 Test 配置；确认 worker 和 Runtime 环境中不存在 `LESHOUYING_INSTITUTION_KEY`。
3. 使用测试用户 A 创建并分享 Agent；测试用户 B 为该 Agent 创建两个会话，并在其中一个会话连续成功使用三次。
4. 核对三次均没有充值订单、钱包 debit，免费 `used_count=3` 且 `reserved_count=0`。
5. 第四次发送得到 402，核对没有 Turn、Message 或 Agent 调用。
6. 在任一订单到账前，B 分别从两个会话产生充值 intent，并创建二维码支付（C扫B）订单；随后立即人工完成两笔测试付款。这样可避免第一笔到账后的全局余额阻止第二个会话产生充值提示。
7. 核对验签回调把内部订单变为 `credited`，余额只增加一次，资金流水只增加一条。
8. 主动查原订单，核对平台结果、回调结果和内部订单一致，且不会重复入账。
9. 任一充值到账后，使用第四次返回 402 的**原始** `usageId` 原子恢复同一任务；前端不得为这次恢复生成新的 `usageId`。核对 Runtime 只创建一个 Turn 和用户 Message、只启动一次 Agent，钱包先预留并在成功后只生成一条固定金额 debit。
10. 在第 9 步成功后再次重放同一 `usageId`，核对返回第 9 步的原 Turn 与结果，且不再启动 Agent、扣费或写入任何资金流水。
11. 错误签名可用无密钥的合成回调验证固定失败 ACK。有效签名的重复、金额不符和商户不符回调只能由服务商重发，或由不输出密钥与原文的受信任 Test 工具验证；不得从浏览器或普通脚本伪造。
12. 检查账本等式、结构化日志和监控，确认没有密钥、完整签名原文、完整回调或完整收银台 URL。

安全证据只记录：

- 内部充值订单号。
- 脱敏的平台订单号。
- 支付/入账状态。
- 金额（分）。
- 对应流水数量。
- 事件时间与低敏 traceId。

不得保存或输出机构密钥、完整回调、完整签名串、完整收银台 URL、付款码或 openid。

## 初版提出的服务商确认清单

本文没有保存下列事项的逐项书面确认状态；后续支付成功报告不能替代全部确认。渠道名称随 2026-08-04 至 2026-08-05 的实现调整，再次联调前应核对当前商户合同。

- 二维码支付（C扫B `/v3/prepay`）的 `pay_type` 枚举与 `qrcode` 响应字段在当前商户配置下的准确值。
- 所有下单和查单响应是否必定带 `sign`，以及签名字段是否与请求规则完全相同。
- `/v3/queryorder` 按 `trade_no` 查询时是否仍返回 `pay_trace_no`、`pay_time` 和 `total_amount`。
- `PAY_SUCCESS` 在二维码支付预下单响应中是否只表示预支付创建成功。
- 交易回调的 `trade_type`、`attach`、`end_time` 字段是否稳定提供，以及回调重试间隔和最大次数。
- Test 可用的最小金额、支付工具、退款限制及测试资金处理方式。
- 二维码支付订单过期后平台订单的最终状态与推荐处理；本轮不调用关单。
- 回调源地址范围和峰值速率，确认每 IP 每分钟 600 次的初始限流不会误伤。
- 平台订单号的唯一性范围，以及跨测试/正式环境是否可能重复。
