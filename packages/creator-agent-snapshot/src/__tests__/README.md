# Snapshot 与 AgentVersion 测试说明

本目录覆盖 `INV-001`、`INV-002`、`INV-003`、`INV-006`、`INV-022` 相关的 E1 证据。

- canonical JSON 测试检查对象顺序、Unicode、数字和非法值。
- Snapshot 测试检查创建顺序、mtime、mode、单 byte 变化、长路径、文件数和大小边界；独立资源边界测试把同一份 digest-bound Manifest fixture 的文件数与展开字节 N-1/N/N+1 送入生产 `parseSnapshotManifest`，并把真实非稀疏 UTF-8 单文件的 10 MiB N-1/N/N+1 送入 `buildSnapshotFromProject`，对两个合法边界完整执行 `verifySnapshotArchive`。metadata 压缩对象测试继续把 50 MiB N-1/N/N+1 送入四个公开数值 owner；独立 `compressed-exact-boundary.test.ts` 则从 compact SHAKE256/base32 recipe 现场写出非稀疏 Project，顺序重建 52,428,799/800/801-byte 单 frame canonical tar.zst：N-1/N 完整通过 builder 与 verifier，N+1 先完成 raw zstd、生产 tar parser与canonical recompress，再由 builder/verifier稳定拒绝。fixture 不提交大对象、不在 CI 搜索 recipe，并固定 Node sync wrapper 空 frame 的 conditional normalization provenance。该本机 `SNP-008` implementation PASS 不冒充尚未运行的 Linux SHA-bound G1 evidence。压缩比测试用 99/100/101 数值 probes 锁定整数比较，再现场生成 1 MiB counter-hex accepted archive 与 1 MiB ASCII `a` canonical bomb；前者完整 verify，后者得到稳定 ratio error，fake S3 finalize 不产生 preparation、final、commit 或 reader visibility，并清零 unwrap key。相对路径边界测试使用真实 ASCII/CJK/astral 混合目录，把 511/512/513 UTF-8 bytes 三个 digest-bound probe 送入 `buildSnapshotFromProject`；前两个完整执行 `verifySnapshotArchive`，513 bytes 以 `SNAPSHOT_PATH_TOO_LONG` 在 verifier 前拒绝。该本机证据不冒充 T0 Linux/E1，component 255-byte 政策仍未冻结，`SNP-009` 保持 `planned`。
- `manifest-canonical-byte-maximum.test.ts` 证明4 MiB只能作为raw/encrypted defense cap：全字段可达canonical maximum为2,536,575 bytes。recipe分别证明path JSON转义总量2,046,001、受总展开量约束的size十进制位数总量12,010和固定骨架/对象开销；真实N-1/N完整parse，exact N+1在raw JSON parser前拒绝且错误不回显canary。
- 根级 `pnpm vnext:test:g0` 会把本目录的 manifest canonical maximum 与 path boundaries 同时纳入正式T0矩阵；设置只供该CI使用的 `VNEXT_T0_JUNIT_FILE` 时，Vitest同时保留默认输出并写入一份固定路径JUnit。该机制在本机通过只证明artifact生成可用，仍需clean SHA上的Linux workflow与GitHub artifact digest才能成为正式证据。
- hostile corpus 测试使用真实 symlink、hardlink、sparse file、Secret、NUL、二进制，以及手工构造的 traversal、link 和特殊 tar header；lone surrogate 在 manifest/tar 产生 bytes 前拒绝，escaped surrogate 与 direct-header/PAX malformed UTF-8 均 fail closed 且错误不回显输入。相对路径 corpus 另以全部 65 个 C0/C1 和双 lone surrogate 驱动 `canonicalizeSnapshotPath` 与 raw Manifest parser，固定错误只含安全 code/message；Protocol 包同时驱动 `SnapshotPathSchema` 与完整 Manifest schema，共形成 268 个 owner 结果。
- raw-ingress hostile boundary 测试把同一份 76-probe corpus送入生产 `parseSnapshotManifest`，锁定五类 malformed UTF-8、lone surrogate、62 个 forbidden C0/C1 和六类 raw structural输入；它只断言稳定错误、无回显和 input bytes不变，不冒充S3/PG业务副作用或完成 `SNP-010`。
- encryption 测试包含 NIST AES-256-GCM 已知答案向量、冻结 `CSNPENC1` binary golden、权威 Envelope/AAD 逐字段绑定、canonical base64url/长度边界、随机生产 nonce 和 bit flip 失败。
- AgentVersion 测试检查显示元数据不进入摘要、可变执行语义会改变摘要、冻结的 Alpha IO 之外输入直接拒绝、仓库不可覆盖和 Conversation 固定版本。独立资源边界测试复用 Protocol 的四个 AgentVersion cases，把 N-1/N/N+1 共 12 个变体送入生产 `buildAgentVersion`；合法边界锁定目标值、稳定摘要与深冻结，超限输入只返回不回显目标值的 `AGENT_VERSION_INVALID`。其中 `developerInstructions=32` 仍是待独立 policy ADR 的实现上限。
- `agent-version-digest-semantics.test.ts` 复用一份digest-bound compact corpus，从同一权威Manifest独立生成原pretty、compact和递归reverse-key pretty三种raw JSON，证明raw bytes不同而canonical manifest/component/version digests逐字相同；随后分别执行Snapshot digest、Behavior一字节、Codex artifact、protocol schema、model和effort mutation。它只登记`AVR-001/003/004/006`；display statistics、IOContract第二合法语义、最大合同E2与PG/API Idempotency仍保持planned。
- Context Tools 闭世界测试把 Protocol 的七个 digest-bound tuple 变体送入生产 `buildAgentVersion`，只把 exact 三工具顺序计为接受，并验证拒绝错误不回显 canary。
- property 测试记录 seed，并对目录顺序、JSON key 顺序、内容 mutation 和 collision 运行重复生成检查。
- `cross-process-golden.mjs` 由独立 Node 进程加载构建后的包，复核 tar/zstd golden digest。macOS 本地和 Linux CI 设计为运行同一向量，任一平台或 zstd 版本漂移都会失败；只有 CI 实际产出 Linux 结果后才形成跨平台证据，本机通过不能代替该结果。
- `object-storage.test.ts` 使用可观测 fake S3 验证两条 exact Signed PUT、完整 header 绑定、100 路 finalize、verify-before-prepare、commit 前不可见、archive final 后 manifest 故障、原 temp 重放、原 temp 丢失后新 DEK/nonce exact replay、commit 存在但 final 缺失与 selected temp 损坏时的 fail-closed/read-repair、不同 cipher generation 并发收敛、损坏 temp 后同 digest 重试、body/size/checksum/metadata hostile mutation、跨 Creator 调用和 key unwrap 后清零。
- `upload.test.ts` 验证 Worker 先完整复核 Snapshot、再使用 create-only authority 生成 DEK，随后形成可直接交给 upload-session 的双密文 contract；同时复核 checksum、独立 nonce、完整解密和 provider key buffer 清零。
- `object-storage.minio.integration.test.ts` 只能由 `scripts/run-minio-e2.mjs` 显式启动：脚本创建固定版本、tmpfs、随机 loopback port 的 disposable MinIO，运行真实 SigV4 双 PUT、缺 SignedHeader 拒绝、32 路 finalize、损坏 temp 重试、archive final 后 manifest failpoint、commit 前不可见、原 temp 重放、原 temp 丢失后的新 DEK/nonce exact replay、commit 已存在但 final 缺失后的 reader fail-closed 与修复、不同 cipher generation 并发收敛与特权篡改检测，然后删除容器和临时 credential 文件。

默认 `test` 不隐式要求 Docker，并排除 `.integration.test.ts`；显式 `test:minio:e2` 产生真实 MinIO adapter 的 E2 组件证据。它仍不测试 PostgreSQL、正式 IAM、真实 RFC3394 wrap/KEK/KMS、Retention、备份或 DR，也不能单独宣称 Gate 1 完整通过。
