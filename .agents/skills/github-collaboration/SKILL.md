# GitHub 开源项目协作

把开源贡献视为具有明确角色、所有权、质量门禁和清理步骤的完整生命周期。默认分支所在的主检出目录只作为控制面，每项改动都在独立的关联工作树中完成。

## 明确任务边界

1. 遵守当前仓库的 `AGENTS.md`，按本次改动读取相关目录说明和贡献约定；已读且未变化的内容无需重读。准备 PR 时读取模板与适用 CI；涉及安全报告或社区行为时再读取对应政策。疑似安全漏洞使用私密安全报告渠道，不要创建公开 Issue。
2. 确认贡献符合项目方向。对于非简单功能，如果仓库政策要求事先讨论，应关联已获接受的 Issue 或 Discussion；不要根据未经接受的路线图假设投入实现工作。
3. 确认当前有效的需求、产品契约或 Issue，记录目标、范围外内容和完成标准。只有有效需求互相冲突、目标版本或环境无法确定，或拟改变已确认产品目标时，才暂停相关改动并请维护者裁决。目标明确的代码缺陷应继续修复；已有授权不重复请示。
4. 记录任务类型、简洁短名、关联 Issue 或需求、验收条件、规范上游基线、贡献者角色、负责人、预期测试、贡献签署要求，以及用户是否授权提交、推送、创建拉取请求、合并或清理。
5. 任务身份必须包含仓库、负责人、工作树绝对路径、任务分支、基准远端与分支、创建时的基准提交 SHA、当前 `HEAD` SHA 和工作树是否有改动。分支名和 URL 是可变入口，不能代替提交 SHA。
6. 创建分支前先判断 Git 远端模型：
   - **有直接写权限的协作者：** `origin` 是规范上游仓库，同时作为基准远端和推送远端。
   - **派生仓库贡献者：** `upstream` 是规范上游仓库和基准远端；`origin` 是贡献者自己的派生仓库和推送远端。
7. 只有现有专用工作树与当前任务明确对应时才复用。当前目录已经是关联工作树时，不要因此再创建嵌套工作树。
8. 按本次请求定义完成条件，持续完成范围内的实现、检查和必要修复。仅执行任务涵盖的阶段，不把未请求的 PR、合并或部署作为本地修复的前置条件。除非用户另外明确授权，否则本流程不包含部署；部署证据要求不能推导出部署授权。

分流 Issue、接受功能、分配所有权、处理已放弃贡献，或区分贡献者、评审者和维护者决策时，读取 [governance-and-contributions.md](references/governance-and-contributions.md)。设置本地克隆、分配并发智能体、交接或恢复所有权时，读取 [local-agent-workflow.md](references/local-agent-workflow.md)。
需要启动本地服务、提供体验地址、使用 Mock、描述验证状态或交接到部署流程时，读取 [facts-and-delivery-evidence.md](references/facts-and-delivery-evidence.md)。

## 创建隔离工作树

1. 从 `git worktree list --porcelain` 第一项所指向的主检出目录操作。它是控制面，不是开发空间。
2. 要求控制面没有受跟踪文件改动。报告并保留未跟踪文件。
3. 检查 `git remote -v`；不要仅凭远端名称推断仓库所有权。记录 `<base-remote>` 和 `<push-remote>`，然后在不切换默认分支的情况下获取远端更新：

   ```bash
   git fetch --prune <base-remote>
   git fetch --prune <push-remote> # 两者相同时省略
   ```

4. 按以下顺序解析基线：用户明确指定的规范上游远端分支、`refs/remotes/<base-remote>/HEAD`，然后是唯一明确的 `<base-remote>/main` 或 `<base-remote>/master`。确认提交存在，并记录 `git rev-parse <base-ref>^{commit}` 返回的不可变基准 SHA；不要假设可能过期的本地分支是最新基线。
5. 按 [naming-and-commits.md](references/naming-and-commits.md) 生成分支名和工作树名。运行 `scripts/worktree_guard.py plan-create --base-remote <base-remote> --push-remote <push-remote>`，检查无效命名、控制面受跟踪改动、已有本地或推送远端分支、已登记工作树和路径冲突。
6. 从解析后的规范上游基线引用一次性创建分支和工作树。有直接写权限的协作者通常使用 `origin/main`，派生仓库贡献者通常使用 `upstream/main`：

   ```bash
   git worktree add -b <type>/<task-slug> <sibling-worktree-path> <base-ref>
   ```

7. 使用 `git worktree list --porcelain`、`git status --short --branch` 和 `git merge-base --is-ancestor <base-ref> HEAD` 验证结果。

生命周期状态、不变量和恢复规则见 [worktree-lifecycle.md](references/worktree-lifecycle.md)。

## 在任务工作树中开发

1. 从任务工作树启动智能体，加载该检出的说明。Combo 新工作树在安装依赖或首次编辑前运行 `bash scripts/dev-preflight.sh`；它自动解析规范上游与推送远端，也接受已确认的 `--base`、`--base-remote` 和 `--push-remote`。遇到克隆、磁盘或环境问题时，按需读取 [开发环境说明](../../../docs/reliable-development-and-preview.md) 的相关章节；其中 Preview 章节仅用于已包含部署的任务。
2. 向智能体提供 Issue、范围、验收条件、非目标、质量命令和授权边界。不得让两个智能体同时拥有同一工作树的写权限。
3. 控制改动范围。不要编辑其他工作树、移动共享分支引用、改写其他智能体的提交历史，或删除其他智能体的文件。
4. 编辑前检查已有改动，保留用户工作，绝不读取或复制凭据与密钥。
5. 迭代时运行范围最小且相关的测试。行为、公共接口、文件、模块职责或用户可见操作发生变化时，同步更新测试和文档。
6. 当任务包含创建提交时，使用约定式提交生成可评审的提交。遵守仓库已经写明的开发者原创声明、贡献者许可协议、提交签名、作者身份和许可证要求，不自行创造规则。不要混入与任务无关的清理。
7. 从任务工作树启动服务前，核对端口占用进程的 PID、命令和当前目录。服务运行期间不要在该工作树切换分支；`HEAD` 或构建输入变化后，停止旧进程，按仓库说明重新构建并启动，再记录新的运行身份。

## 通过拉取请求前的质量门禁

1. 再次获取规范上游基准远端，并检查相对于选定基线的完整任务差异：

   ```bash
   git fetch --prune <base-remote>
   git diff --stat <base-ref>...HEAD
   git diff --check <base-ref>...HEAD
   git log --oneline <base-ref>..HEAD
   ```

2. 检查所有改动文件和未跟踪文件。验证正确性、边界条件、错误处理、兼容性、安全性、测试、文档、生成文件和意外敏感信息。
3. 执行仓库要求的全部本地质量门禁，不得只运行离改动最近的测试。以持续集成和贡献文档中的命令为准。Combo 的门禁和按风险增加的检查见 [quality-and-pull-requests.md](references/quality-and-pull-requests.md)。
4. 运行 `scripts/worktree_guard.py check-pr-ready --base-remote <base-remote> --push-remote <push-remote>`。解决工作树不干净、分离头指针、缺少或错误的推送上游、未推送提交、冲突、空差异，以及分支落后于规范上游基线等问题。
5. 规范上游基线前进时，按仓库政策更新任务分支。未发布且仅由本人使用的分支可以在安全时变基；分支已经共享后，不要改写历史或强制推送，除非仓库政策允许且用户明确授权。
6. 验证证据必须绑定实际执行时的 `HEAD` SHA。涉及可运行产品时，明确数据和登录模式属于 `Real`、`Mock` 还是 `Mixed`，并按实际覆盖范围使用“静态页面可评审”“Mock 流程可体验”“局部真实链路已验证”或“完整真实链路已验证”等准确表述。

## 通过拉取请求协作

1. 除非用户请求已经包含相应外部写操作，否则不要推送或创建拉取请求。
2. 只把任务分支推送到记录的推送远端，并设置其上游。有直接写权限的协作者创建同仓库拉取请求；派生仓库贡献者创建从 `origin:<branch>` 到 `<base-remote>:<base>` 的跨派生仓库拉取请求。不得把派生仓库贡献者的分支推送到规范上游远端。
3. 向记录的规范上游基线创建拉取请求，不得把当前恰好检出的分支当作目标。遵守仓库拉取请求模板和贡献签署要求。
4. 拉取请求标题使用约定式提交格式。正文说明问题、方案、范围、基准 SHA、当前提交 SHA、实际验证命令与结果、未验证项、风险、兼容性或迁移影响；涉及运行体验时还要说明环境身份以及 Real、Mock、Mixed 边界。视觉行为变化时附截图，并关联 Issue。
5. 按仓库明文规定的作者类别执行复核路径。仓库允许列名授权维护者单人闭环时，该维护者可以复核并合并自己或他人的拉取请求，但必须在拉取请求中留下绑定当前候选提交的合并核验记录；其他作者的改动仍须授权维护者独立复核并批准。不得仅凭用户名、组织身份或仓库权限推断项目授权。
6. 在同一工作树中解决阻塞性反馈；对发现的缺陷补充测试；推送后续提交。候选提交、目标分支、合并基点或实际差异变化后，重新执行适用的复核路径并刷新当前提交的检查；只有问题已修复或处理决定已有记录时，才能解决评审讨论。
7. 要求分支与规范上游基线保持同步，并且当前提交上的 GitHub 必需检查全部通过。较早提交上的检查结果不能证明当前提交质量。
8. 只有用户已授权合并、分支保护允许、作者类别适用的复核条件已经满足且没有阻塞讨论时才能合并。仓库明文允许的授权维护者单人闭环不是管理员绕过；仍不得绕过失败或缺失的必需检查、讨论解决要求、分支保护或用户对具体外部写操作的授权。
9. 使用仓库已经配置的合并策略。没有书面政策时，不要自行决定压缩合并、变基合并或合并提交。

## 验证合并并清理

1. 查询拉取请求，记录编号、状态、基线、来源分支、可获得的合并方式、合并提交和合并时间。已关闭但未合并的拉取请求不属于已完成工作。
2. 获取远端更新，并确认合并结果已经进入解析后的规范上游基线引用。对于压缩或变基合并，应通过拉取请求元数据和最终差异验证，不能假设旧分支顶端提交仍是规范上游基线的祖先。
3. 确认任务工作树没有已修改、已暂存、未跟踪、冲突或未推送工作，并且没有智能体、编辑器、测试进程或开发服务继续使用它。
4. 运行 `scripts/worktree_guard.py plan-cleanup` 生成不执行实际删除的清理计划。检查精确路径、分支、顶端提交、基线、拉取请求证据和合并策略。
5. 从控制面移除干净工作树，不使用 `--force`，然后删除本地分支。Git 能验证祖先关系的合并提交使用普通 `-d`；已经独立核实的压缩或变基合并才可使用 `-D`，因为此时 Git 无法从祖先关系证明已合并：

   ```bash
   git worktree remove <exact-worktree-path>
   git branch -d <branch> # Git 能验证祖先关系的合并提交
   git branch -D <branch> # 仅限已核实的压缩或变基合并
   git worktree prune --dry-run
   ```

6. 让 GitHub 已配置的自动删除功能处理远端来源分支；或者仅在明确授权后，从记录的推送远端删除精确任务分支。清理派生仓库贡献时绝不能删除规范上游分支，也不能推断用户允许删除远端引用。
7. 拉取请求被放弃时，保留工作树，直到用户明确决定归档、调整目标或丢弃。不得通过强制移除不干净的工作树让清理表面通过。
8. 汇报拉取请求结果、合并提交、检查和适用的复核证据（授权维护者合并核验记录或独立批准）、已移除工作树、本地与远端分支状态，以及有意保留的内容。严格区分已开发、已验证、已提交、已推送、持续集成通过、已合并和已部署；每个结论都附对应证据。

恢复或清理涉及过期元数据、缺失目录、锁定工作树或强制删除时，先读取 [worktree-lifecycle.md](references/worktree-lifecycle.md)。
