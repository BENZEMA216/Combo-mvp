# 开源贡献者与多智能体本地协作

## 选择贡献模型

有规范上游仓库写权限的协作者直接克隆项目，`origin` 同时作为基准远端和推送远端：

```bash
git clone <canonical-repository-url> <repo>
cd <repo>
git remote set-head origin --auto
git fetch --prune origin
```

没有写权限的外部贡献者先在 GitHub 创建派生仓库，再克隆自己的派生仓库；`origin` 只负责推送，`upstream` 指向规范上游仓库并提供基线：

```bash
git clone <contributor-fork-url> <repo>
cd <repo>
git remote add upstream <canonical-repository-url>
git fetch --prune origin
git fetch --prune upstream
git remote set-head origin --auto
git remote set-head upstream --auto
```

先用 `git remote -v` 核对所有读写地址，避免把贡献分支推错仓库。不要假设名为 `upstream` 的远端一定是官方仓库；以用户给出的项目地址和 GitHub 拉取请求目标为事实来源。

用户只需要一个主克隆目录，并把默认分支检出目录作为控制面。安装依赖和本地工具时遵守仓库 README 与贡献指南。不要把密钥提交进 Git；若 Codex 托管工作树需要被忽略的本地文件，只在仓库已经审查 `.worktreeinclude` 后复制，并保持最小范围。

## 给智能体的任务契约

开始任务时至少提供：

```text
目标：<要改变的用户或系统行为>
需求真源：<当前有效的用户指令、Issue、需求或产品契约>
验收条件：<可验证结果>
范围：<允许修改的模块>
非目标：<不要顺手做的事情>
规范上游仓库：<owner/repo>
基线：<base-remote>/<branch>@<immutable-sha>
推送：<push-remote>/<task-branch>
工作树：<absolute-path>
分支：<type>/<task-slug>
验证：<针对性测试 + 仓库质量门禁>
运行模式：<不适用 / Real / Mock / Mixed；Mixed 时逐项说明>
授权：<仅本地 / 可提交 / 可推送和创建拉取请求 / 可合并 / 可清理>
```

智能体启动后先报告它解析到的仓库根目录、工作树、分支、基线和说明文件。实际状态不一致时，先停止写入并解释偏差。

## 并发模型

- 主用户负责任务分配、跨任务优先级和最终合并顺序。
- 开发智能体对自己的工作树拥有唯一写权限。
- 复核智能体从拉取请求差异或单独的只读检出目录工作；默认不修改作者工作树。
- 派生仓库贡献者只向自己的 `origin` 推送；维护者不得要求贡献者必须把分支直接推到规范上游仓库才能接受复核。
- 两项功能存在依赖时，优先让下游以已经发布的上游分支为显式基线，并在拉取请求中标注堆叠依赖。上游合并后，再把下游更新到主分支。
- 多个拉取请求修改同一热点文件时，提前确定合并顺序并逐个更新基线，避免所有智能体同时解决相同冲突。

## 日常交互

用户可以随时要求智能体报告以下最小状态：

```text
任务 / 负责人 / 需求真源
工作树 / 分支 / 基线 SHA / 当前 HEAD SHA / dirty
当前阶段
改动摘要
已运行与待运行检查
未提交 / 未推送状态
运行环境 / 进程当前目录 / 组件 SHA / Real、Mock、Mixed 边界
拉取请求与阻塞项
下一步及所需授权
```

不要用“应该已经推送”之类自然语言代替 Git 状态和拉取请求元数据。智能体离开任务前应提供相同格式的交接信息，让接手者能从确定状态继续。

## Codex 特有行为

- 仓库级技能位于 `.agents/skills`，从仓库任意子目录启动的新 Codex 会话都能发现它。
- `AGENTS.md` 在会话启动时加载。修改后应开启新会话验证，不要假设正在运行的会话自动获得新说明。
- Codex 桌面端托管工作树默认可能处于分离头指针状态；准备提交和拉取请求前先创建任务分支。
- Git 不允许同一分支同时在两个工作树中检出。需要在前台继续工作时，使用受支持的会话交接，或先从原工作树释放该分支。
- Codex 自动清理托管工作树的策略不能替代项目生命周期。永久工作树和命令行创建的工作树必须按本项目流程显式清理。
