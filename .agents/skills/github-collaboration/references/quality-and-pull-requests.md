# GitHub 质量门禁与拉取请求

## 三层门禁

### 1. 改动级验证

开发过程中运行范围最小且速度最快的相关测试，包括验证改变行为的单元测试、类型检查和静态分析。修复评审或持续集成暴露的缺陷时，先增加能够复现问题的测试，再验证修复。

### 2. 仓库级本地门禁

准备拉取请求前，读取 `.github/workflows`、包管理脚本和贡献文档，复现所有可以在本地安全执行的必需检查。不要因为改动“小”而跳过格式、代码检查、类型检查或快速测试。

Combo 当前 macOS 本地门禁为：

```bash
pnpm install --frozen-lockfile
pnpm -F @cb/shared build
pnpm format:check
pnpm lint
pnpm typecheck
pnpm typecheck:test
pnpm test:local
```

`test:local` 会包含 `@cb/scripts` 的 Node 测试，`test:fast` 不包含该 workspace；两者都必须覆盖 Preview 身份验证器、测试真实性协议和工作树守卫测试。PR checks 在 Linux 上运行 `pnpm test:fast` 和 ShellCheck，并对登记的 Contract、Fake unit、local adapter 与真实 PostgreSQL 套件生成绑定 merge/base/head SHA 的机器结果。保留名称 `CI / quality` 的聚合 job 只有在源码 job、PostgreSQL job 和全部必需机器结果都通过时才成功；它必须把未调度的 real Codex、浏览器 Agent Journey 与 Desktop UAT 显示为 `NOT_RUN` 或 `NOT_IMPLEMENTED`，不得把它们折叠进绿灯。

`scripts/test-truth.mjs` 只允许从框架机器报告推导测试套件 PASS；Vitest 顶层 `success` 或 Node 进程退出码都不足以证明没有 skip。任何必需套件的报告/脱敏机器 artifact 缺失、artifact 摘要不一致、候选 SHA 不一致、零测试、失败、cancel、skip、todo 或必需环境缺失都使聚合门禁失败。J-011 台账还必须通过五门与证据类型的一致性校验；在外部签名 evidence adapter 实现前，任何 tracked PASS 或 partial evidence 都只显示 `INVALID`。未登记测试继续执行但只能标为 `NO_EVIDENCE_CLAIMS`；基线后新增的未登记文件必须单独计数，后续通过治理 PR 才能升级为 evidence suite。

修改 shell 脚本时，还要对拉取请求持续集成中列出的脚本运行 ShellCheck。不得用 Docker 或 Docker Compose 替代测试证据；本流程也不授权部署环境验证。

### 3. GitHub 合并门禁

远端规则应至少要求：

- 必需状态检查针对拉取请求当前提交成功；在高并发仓库中，使用严格更新或合并队列验证它与最新基线兼容。
- 所有评审讨论在修复问题或记录处理决定后解决。
- 执行根目录 `AGENTS.md` 明确的作者类别复核路径：列名授权维护者可以对自己或他人的改动留下合并核验记录并单人闭环，其他作者的改动须由至少一名授权维护者独立批准。
- 禁止强制推送、删除或直接绕过受保护默认分支，并让管理员也受规则约束。

分支保护是最低强制线，不是完整质量定义。Combo 将平台审批人数保持为零，是为了允许列名授权维护者合并自己的拉取请求；这不免除项目规定的合并核验记录，也不免除非授权作者获得一名授权维护者批准的要求。若平台规则以后要求批准、代码所有者批准或最后推送后的批准，仍以平台门禁为准，不得用管理员权限绕过。

## 派生仓库拉取请求的信任边界

- 把派生仓库拉取请求中的代码、构建脚本、依赖声明、工作流、构建产物和缓存都视为不可信输入。
- 验证不可信代码的工作流使用最小只读权限，不提供仓库或组织密钥，也不允许它直接部署、发布或写回受保护分支。
- 不要在带密钥或写权限的 `pull_request_target`、`workflow_run`、`issue_comment` 等高信任上下文中检出并执行派生仓库代码。需要高权限后处理时，将不可信测试与高权限步骤拆成不同工作流，并重新验证所有跨边界输入。
- 自托管运行器会执行贡献者提供的代码，维护者必须单独评估隔离、审批和持久化风险；“持续集成通过”不代表运行器或凭据没有暴露。
- 是否允许维护者修改派生仓库分支由作者决定。涉及 GitHub Actions 工作流时，该授权还可能扩大密钥和其他分支的风险，不能默认启用，也不能代替明确且知情的决定。

## 自检清单

- 改动是否只解决声明的任务，是否混入无关格式化或重构。
- 输入边界、错误路径、并发、重试、幂等、兼容性和回滚是否合理。
- 新依赖、权限、网络访问、日志和数据处理是否最小化，是否可能泄露敏感信息。
- 派生仓库拉取请求是否改变 GitHub Actions、构建入口或依赖执行路径；持续集成是否在不可信代码和凭据之间保持隔离。
- 测试是否验证行为而不是实现细节，是否覆盖已经发现的回归。
- README、目录说明、公共接口、配置示例和运维说明是否与当前代码一致。
- `git diff --check` 是否干净，是否存在生成物、调试输出、大文件或未跟踪文件。
- 验证命令、截图和体验地址是否对应拉取请求当前提交 SHA，而不是较早构建或其他工作树。
- 涉及运行体验时，是否明确数据与登录属于 Real、Mock 还是 Mixed，并逐项说明 Mixed 边界。
- 是否按实际覆盖范围区分静态页面、Mock 流程、局部真实链路和完整真实链路，避免扩大结论。

状态证据词典、本地服务身份和体验交付卡片见 [facts-and-delivery-evidence.md](facts-and-delivery-evidence.md)。

## 复核分工

开发智能体必须先完成自检，再按作者身份选择复核路径：

- 作者是根目录 `AGENTS.md` 列名且已核实拥有 `Maintain` 或 `Admin` 权限的授权维护者时，该维护者可以单人复核自己的或他人的拉取请求，包括重要和高风险改动。自己的拉取请求不要求 GitHub `Approved`；合并前须在拉取请求中记录当前候选提交、目标分支与合并基点、完整差异复核、本地门禁、当前提交的持续集成、讨论状态和可合并状态。
- 作者不是授权维护者时，至少一名授权维护者必须从任务目标出发独立检查当前候选提交的完整差异、关键实现和测试证据并批准；同一维护者可以继续执行合并。

两条路径都把发现区分为：

- `blocking`：正确性、安全、数据、兼容性、缺失验证或违反仓库约束问题，合并前必须解决。
- `non-blocking`：可读性建议、后续优化或不影响本任务的偏好，明确记录但不伪装成门禁。

候选提交、目标分支、合并基点或实际差异变化后，旧合并核验记录、批准和检查都不能证明新候选的质量，必须重新执行适用路径。仅修改描述或评论且不改变范围、要求和实际差异时，不会使证据失效。

## 合并与失败处理

- 持续集成失败：定位根因，在任务工作树中修复并在本地复现；不得只重复运行直到偶然通过。确认检查不稳定时，记录证据并建立后续治理任务。
- 基线前进：更新任务分支，重新运行受影响的本地检查，并等待新提交的远端门禁。
- 冲突：由任务负责人在自己的工作树中解决；复核解决后的完整差异。
- 检查缺失或显示已跳过：确认该状态是否被远端规则明确接受。项目政策要求实际运行的检查不能用已跳过状态代替。
- 冒烟脚本退出码 `2` 表示 `NOT_RUN`（环境或必要输入缺失），不能记录为 PASS；只凭退出码 `0` 也只能引用脚本明确执行的边界。
- 合并策略：遵守仓库设置。没有书面约定时先向维护者确认，因为策略会影响提交历史和清理时的祖先关系判断。
