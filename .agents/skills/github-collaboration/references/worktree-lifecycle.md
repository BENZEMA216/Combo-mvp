# GitHub 贡献工作树生命周期

## 状态模型

| 状态           | 进入条件                                                 | 允许的下一步           | 退出证据                             |
| -------------- | -------------------------------------------------------- | ---------------------- | ------------------------------------ |
| 已规划         | 任务、负责人、规范上游基线 SHA、推送远端和验收条件已明确 | 创建工作树             | 远端、提交、命名和路径检查通过       |
| 开发中         | 独立分支已在独立工作树中签出                             | 开发、测试、提交       | 工作树与任务一一对应                 |
| 可创建拉取请求 | 本地完整门禁通过，分支已推送且不落后于基线               | 创建或更新拉取请求     | 防护检查和测试证据                   |
| 评审中         | 拉取请求已打开                                           | 复核、修复、重新验证   | 当前提交的持续集成、评审和讨论状态   |
| 可合并         | 必需检查通过、作者类别适用的复核条件满足、讨论已解决     | 经授权合并             | GitHub 合并区域没有阻塞项            |
| 已合并         | 拉取请求明确显示 `MERGED`，结果已进入规范上游基线        | 清理                   | 拉取请求元数据和规范上游基线中的结果 |
| 已清理         | 工作树、局部分支和相关进程已处理                         | 归档任务               | 清理报告                             |
| 已放弃         | 拉取请求关闭但未合并，或任务取消                         | 保留、转交或经确认丢弃 | 维护者的明确决定                     |

不要跳过状态。尤其不要把“拉取请求已关闭”“持续集成曾经通过”或“分支看起来已合入”当作 `MERGED` 证据。

## 不变量

- 主检出目录是控制面。它承载远端同步、工作树清单和清理操作，不承载任务改动。
- 基准远端与推送远端是两个独立角色。有写权限的协作者通常两者都是 `origin`；派生仓库贡献者通常从 `upstream` 建立基线，只向自己的 `origin` 推送。
- 一个可写任务只属于一个工作树、一个分支和一个负责人。其他智能体可以只读复核，但不得在该工作树中并行写入。
- Git 元数据由所有工作树共享。任何工作树中的 `fetch` 都会更新共同的远端跟踪引用；删除分支、变基、重置和清理过期记录会影响其他工作树，因此必须先解析精确目标。
- 一个分支只能同时被一个工作树签出。需要并行拆分时，为每个子任务创建不同分支和工作树，并通过独立拉取请求或明确的集成分支汇合。
- 工作树路径使用仓库同级目录，避免在仓库内部嵌套。路径必须显式，不得使用宽泛变量、通配符或符号链接推断删除目标。
- 任务记录同时保存可读的基线引用和创建时的不可变基准 SHA。后续基线引用前进不能改变任务最初从哪一个提交开始的事实。
- 工作树中已有服务运行时不切换分支。`HEAD`、依赖、配置或构建输入变化后，停止旧进程并重新构建、启动；端口和 URL 不能在不更新运行身份的情况下代表另一个版本。

## 创建前检查

1. `git worktree list --porcelain`：确认主检出目录、已有工作树及各自的 `HEAD` 和分支。
2. `git status --short --branch`：主检出目录不得有受跟踪改动；未跟踪文件只报告，不移动、不删除。
3. `git remote -v`：确认规范上游仓库、基准远端与推送远端的读写目标。
4. `git fetch --prune <base-remote>`，并在远端不同时获取 `<push-remote>`：刷新远端引用。
5. `git symbolic-ref refs/remotes/<base-remote>/HEAD`：优先解析规范上游默认分支；失败时再检查明确的 `<base-remote>/main` 或 `<base-remote>/master`。
6. `git show-ref --verify refs/heads/<branch>`、`git show-ref --verify refs/remotes/<push-remote>/<branch>` 与路径存在性检查：本地或推送目标存在同名分支时更换任务短名，不复用状态不明的对象。

## 智能体并发与交接

- 每个智能体从自己的工作树目录启动，并在任务记录中写明绝对路径、分支、基线、负责人和当前状态。
- 多智能体协作优先拆成边界独立的子任务。若必须串行接手同一分支，先让原负责人停止写入，提交或明确保留工作区状态，再生成一次状态快照后交接。
- 复核智能体默认只读。需要它直接修复时，先显式转交写权限，不能让原开发智能体同时继续。
- 不在智能体之间复制未提交文件。使用提交、补丁或清晰的交接机制传递，确保来源和差异可审查。

## 清理前检查

必须同时满足：

1. 拉取请求状态是 `MERGED`，且基线与来源分支和任务记录一致。
2. 已获取规范上游远端基线，并能在该基线上确认合并结果。
3. 工作树的受跟踪、已暂存、未跟踪和冲突状态全部为空。
4. 没有尚未推送到贡献者推送远端的提交；远端分支已自动删除时，通过拉取请求来源提交哈希与本地 `HEAD` 比对。
5. 没有智能体会话、编辑器、测试、监视进程或服务继续使用该目录。
6. 操作者已经复核工作树绝对路径、局部分支名和 `HEAD` 对象标识。
7. 已记录或关闭从该目录启动的本地服务；没有端口继续把已清理工作树的旧版本伪装成当前任务。

先执行不带 `--force` 的 `git worktree remove`。普通合并提交可以使用 `git branch -d`；GitHub 压缩合并或变基合并会改写提交关系，只有已经独立核实拉取请求合并证据时，才允许对精确分支使用 `git branch -D`。

## 异常恢复

- 目录被手动移动：优先使用 `git worktree repair <path>`，不要手工修改 `.git/worktrees`。
- 目录已消失但元数据仍在：先用 `git worktree prune --dry-run --verbose` 查看，再执行不带 `--dry-run` 的清理。
- 工作树被锁定：先确认锁定原因和负责人；只有已知安全时才使用 `git worktree unlock`。
- 工作树不干净：停止清理，列出状态并请求处理方向。不要用 `--force` 掩盖问题。
- 拉取请求关闭但未合并：进入“已放弃”状态，默认保留。删除分支或工作树前，需要维护者明确决定如何处置尚未合并的提交。
