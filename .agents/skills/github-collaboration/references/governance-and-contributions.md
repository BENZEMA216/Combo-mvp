# 开源贡献治理与角色

## 角色不等于权限猜测

- **贡献者**提出 Issue、设计说明、代码、测试或文档，并对自己的贡献分支负责。
- **任务负责人**拥有某个工作树的单一写权限，维护范围、状态和验证证据；负责人可以是人或智能体。
- **评审者**按仓库规定的作者类别复核路径检查目标、差异、测试和风险，给出评论、批准或请求修改；完成评审并不自动获得合并权限。
- **维护者**代表项目接受范围、解释仓库政策、管理标签和里程碑、指定评审者，并在全部门禁满足后决定是否合并。
- **授权维护者**是根目录 `AGENTS.md` 明确列名且当前具有仓库 `Maintain` 或 `Admin` 权限的维护者。名单与权限缺一不可；名单变更只有进入默认分支后才生效。

不要根据组织成员关系、历史活跃度、`CODEOWNERS` 或单独的仓库权限推断授权维护者身份。以默认分支上的授权名单和操作时核实的仓库权限为共同事实来源。

## 贡献进入流程

1. 先搜索现有 Issue、Discussion 和拉取请求，避免重复实现。
2. 小型且明确的缺陷修复或文档修正可以按仓库政策直接提交拉取请求；大型功能、公共接口、架构、兼容性、数据模型或治理变化，应先取得维护者对问题和范围的共识。
3. Issue 已创建不代表功能已被接受，留言表达意向也不代表取得写权限。开始前记录负责人、验收条件、非目标和依赖关系。
4. 安全漏洞使用 `SECURITY.md` 指定的私密渠道；行为问题按行为准则指定的执行渠道处理。不要为了透明而公开敏感报告或个人信息。
5. 仓库没有写明服务时限、贡献者许可协议、开发者原创声明、审批人数、合并策略或维护者身份时，报告缺口并请求决定，不自行创造政策。

## 公开且可追溯的决定

- 把范围确认、重要取舍、阻塞原因和后续事项记录在关联 Issue 或拉取请求中，让没有参与智能体对话的贡献者也能理解。
- 智能体对话、私聊和本地日志不是项目决策的唯一事实来源。需要长期有效的结论应回写到 GitHub 协作记录或仓库文档。
- 将超出当前拉取请求范围的有效建议转成关联 Issue，不要求贡献者无限扩大原任务。
- 明确区分项目政策、阻塞性质量问题和评审者个人偏好。

## 复核与合并路径

- 授权维护者可以单人复核并合并自己或他人发起的拉取请求，包括重要和高风险改动，无需第二账号，也不要求在自己的拉取请求上产生 GitHub `Approved`。合并前必须在拉取请求描述或评论中留下合并核验记录，至少包含当前候选提交 SHA、目标分支和合并基点、完整差异复核、`blocking` 与 `non-blocking` 结论、本地门禁、当前提交的持续集成、未解决讨论和可合并状态。
- 非授权维护者、外部贡献者或机器人发起的拉取请求，仍须至少一名授权维护者独立复核并批准当前候选提交。该维护者可以同时合并，不要求另一名合并者。
- 候选提交、目标分支、合并基点或实际差异变化后，旧合并核验记录、批准和检查全部失效，必须重新执行适用路径。仅修改描述或评论且不改变范围、要求和实际差异时，不会使证据失效。
- 单人闭环仍须满足当前提交的必需检查、最新基线兼容性、讨论解决、分支保护和用户对具体外部写操作的授权。角色授权不自动授权智能体评论、批准、合并、部署、发布或处理其他拉取请求。

授权维护者使用以下最小结构留下合并核验记录：

```text
合并核验记录
候选提交：<head SHA>
目标与基点：<base ref> @ <merge-base SHA>
完整差异：<已复核；blocking / non-blocking 结论>
本地门禁：<命令与结果>
远端门禁：<当前候选提交上的检查与结果>
讨论与合并：<未解决讨论数；可合并状态>
```

## 拉取请求状态与所有权

- `Draft` 表示作者主动邀请早期反馈，但尚未请求最终审批。
- `Ready for review` 表示作者已完成本地门禁，拉取请求描述和测试证据与当前提交一致，并邀请执行作者类别适用的复核路径；它不代表复核条件已经满足。
- `Changes requested` 表示存在阻塞问题；作者或获得明确授权的维护者在贡献工作树中修复后重新请求评审。
- `Approved` 是非授权作者路径的独立批准证据，只对当时的候选提交、目标分支、合并基点和实际差异有效。授权维护者自己的拉取请求使用合并核验记录，不要求自我批准。
- `Merged` 必须由 GitHub 拉取请求状态和规范上游基线共同证明。
- `Closed` 或 `stale` 不代表可以丢弃工作。关闭未合并贡献、接管派生仓库分支或删除远端分支前，应尊重作者所有权并记录维护者决定。

## 维护者质量责任

- 给出可执行且范围明确的反馈，解释阻塞理由，并及时标记已经解决的讨论。
- 不使用管理员权限绕过持续集成、作者类别适用的复核路径、讨论解决要求、分支保护或用户对具体外部写操作的授权。
- 对派生仓库拉取请求保持不可信代码边界，不为方便测试而把密钥暴露给贡献代码。
- 合并策略、版本归属和后续发布由项目政策决定。拉取请求合并不自动授权部署或发布。
- 遵守行为准则，评价贡献内容而不是贡献者身份；治理分歧通过有记录的维护者决策或申诉渠道处理。
